## Problem Statement

### Roles

The stored `owner` role is the admin. Add `warehouse` to the check that today allows only `owner` and `agent`. Warehouse is not an owner.

- Owner: everything, including product create, client archive, invite, removal, receive, correct, book, complete, and cancel.
- Warehouse: receive stock and correct on-hand. No booking, no complete, no cancel, no product create, no archive, no invite, no removal.
- Agent: book, complete, and cancel. No receive, no correct, no product create, no archive, no invite, no removal.

Hide add-order on the client row, the client card, and Orders when the role is warehouse. A warehouse save is rejected with an alert and writes nothing.

### Invite and removal

A signed-in person with no membership still gets the create-company form. That path does not become the invite screen.

The owner gets one entry that is not a dock item. The company name stays visible in the header at phone width, including below 380px. That shown name is a link only for the owner. It opens a screen with the one active code, a control that rotates it, and the member list, including removed memberships. Rotating the code makes the previous code fail. Warehouse and agents see the same shown name as text, not a link, and do not get this screen.

Removal is a control on that list. It sets `removed_at` and keeps the row. The same list has a control on a removed row that clears `removed_at`. Joining with the code does not clear it.

The join page accepts that one code and inserts a membership as `agent`. It does not create a tenant. A wrong code alerts and writes nothing. A person who already has a membership is not given another role on this page.

A membership with `removed_at` is not a member on every request, including one already in progress. The request that finds the removal shows the notice in that membership's locale and signs the session out.

The shared code does not clear a removal. Joining with the code rejects a user whose membership has `removed_at`. A different person with no membership can still join with the code.

### The order

One order holds one or more products. Each line is a whole amount from 1 through 100000. Any other amount alerts and writes nothing. The same product cannot appear twice on one order.

Agents and the owner open the same form. Warehouse does not.

- Clients: the search stays. Each row and the client card get one action, add order. The form opens with that client set. Address choices are that client's addresses, as the trial already does.
- Orders: add order opens the same form with the client empty. The person picks the client, then the address, then stages product lines (product + amount, Add into a list), then saves.

The date and the note that the trial already collects stay on the form. One primary button confirms the booking. The button is disabled while it saves or while the line list is empty.

The booking is one transaction. It locks each line's `stock_balances` row in product-id order, computes free as `qty` minus the amounts on that product's lines whose orders are `open` or `in_delivery`, and inserts the order and all lines only when every amount is not greater than free. Otherwise it alerts and writes nothing. On-hand does not change at booking.

This pass does not add a control that sets `in_delivery`. New orders stay `open` until complete or cancel. The free-stock sum still counts `in_delivery` so an existing row in that status keeps its hold.

The order screen shows every saved product name and amount. That is where complete and cancel live.

Complete is a control on that screen for the agent or the owner. Warehouse has no complete control. In one transaction it locks the order and each line's `stock_balances` row in product-id order. It applies only when the status is still `open` or `in_delivery`. Otherwise it alerts and writes nothing: no status change, no ship move, and no quantity change. When it applies, it sets the order to `completed`, and for each line inserts a `ship` stock move for that amount and decrements `stock_balances.qty` by the same amount in that same write, so the hold does not keep subtracting after on-hand has dropped.

Cancel is a control on that screen for the agent or the owner, and only while the status is `open` or `in_delivery`. It sets `cancelled`, writes no stock move, and leaves `stock_balances.qty` unchanged. A completed order cannot be cancelled by this control.

### Maintenance date

This pass does not add an equipment-model column. The model on the card is the product name. Notes stay in `client_notes`.

Completion stores one next date per client and product. The column is `client_service.next_on`, unique on that client and product. When `maintenance_days` is null, that completion writes no `client_service` row. When it is 14, 30, 90, 180, or 365, the same completion transaction stores the completion calendar day in `tenants.timezone` (default `Asia/Bishkek`) plus that many days. A later completion of the same client and product replaces that date. The client card lists each product name with its `next_on`, and leads with the earliest date. The Due dock item stays disabled.

### The pile

Receive stays the owner path and also allows warehouse. Agents are rejected.

Correction is one control on the product screen for the owner or warehouse. The person enters a new on-hand quantity. A value that is not a whole number alerts before any lock, and writes nothing. Agents are rejected the same way receive rejects them. For a whole number, the write locks that product's `stock_balances` row first and re-reads `qty` and that product's held sum in the same write. Held is the amounts on that product's lines whose orders are `open` or `in_delivery`. If the entered quantity is below the locked held sum, it alerts and writes no balance change and no stock move. If it equals the locked `qty`, it writes nothing. If it is higher, it sets `qty` and writes `correct_in` for the difference from that locked `qty`. If it is lower, it sets `qty` and writes `correct_out` for the difference from that locked `qty`.

The product list's free number is the same free the booking uses, not raw on-hand. Held in that number is the same per-product sum. The detail page shows on-hand, held, and free from those numbers. The detail page stops hardcoding reserved to 0.

### What does not change

Client search by name or phone digits. Oblast, then raion or city. Kyrgyz and Russian strings added in pairs. No English in the interface. Company, client, and product names stay as written. Dock order stays Clients, Orders, Products, Due. Due stays closed.

### R3-1 — completeness (blocking)

**Problem**

> The held-sum check is specified before the lock. The screen alerts when the entered on-hand quantity is below the held sum, and only the passing path locks `stock_balances` and sets `qty`. Booking locks that same row and then inserts a hold, and receive locks it and then adds quantity. Either can commit between this check and this lock. The correction then sets on-hand from a stale read, so `qty` can fall below the held sum and the `correct_in` or `correct_out` difference can disagree with the quantity change. `stock_balances.qty` must stay at least 0, so a later complete of that hold can fail the constraint.

**Remedy**

> Lock that product's `stock_balances` row first and re-read `qty` and that product's held sum in that same write. If the entered quantity is below the locked held sum, alert and write no balance change and no stock move. If it equals the locked `qty`, write nothing. If it is higher, set `qty` and write `correct_in` for the difference from that locked `qty`. If it is lower, set `qty` and write `correct_out` for the difference from that locked `qty`. Keep the whole-number alert before the lock.
